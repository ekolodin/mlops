# Итоговый проект: сервис поиска похожих объектов

Соберите сервис, который ищет по каталогу из **100 000 текстов или изображений**. Например, по фотографии кресла можно найти пять снимков похожих товаров.

В проекте за поиск отвечают три компонента. Предобученная модель с Hugging Face переводит текст или изображение в вектор чисел — **эмбеддинг**. Библиотека FAISS находит ближайшие векторы в каталоге. Через NVIDIA Triton Inference Server клиент отправляет вектор и получает пять идентификаторов (ID). Для полного балла достаточно точного поиска на CPU. Обучение модели, GPU и облачный сервер не нужны.

## Тема проекта

| Тема и данные | Что собрать в каталоге | Что искать |
|---|---|---|
| Архив новостей — [AG News](https://huggingface.co/datasets/sentence-transformers/agnews) | Описания статей без заголовков. Один ID соответствует одной статье. | По заголовку найдите его статью. Если в пятёрку попала новость на ту же тему, проверьте, о том ли она событии. |
| Поиск похожих вопросов — [Stack Exchange Duplicates](https://huggingface.co/datasets/sentence-transformers/stackexchange-duplicates) | Заголовки вопросов. Если один заголовок встречается в нескольких парах, включите его один раз. | Из пары дубликатов оставьте один вопрос в каталоге, а второй подайте как запрос. Проверьте, нашёлся ли первый. |
| Поиск товара по фотографии — [Stanford Online Products](https://cvgl.stanford.edu/projects/lifted_struct/) | Фотографии товаров. У каждого снимка свой ID; отдельно сохраните ID товара. | По снимку, которого нет в каталоге, найдите тот же товар с другого ракурса. Посмотрите, не подобрал ли сервис другой предмет с похожим фоном. |

Можно взять свои данные. Опишите, кто будет пользоваться поиском, с чем придёт пользователь и что захочет получить. Уточните, что означает один ID. Проверьте, что данные доступны проверяющему и после удаления дублей осталось хотя бы 100 000 объектов.

## Как устроен сервис

**До запуска сервера** отберите 100 000 разных объектов и присвойте каждому постоянный целочисленный ID. Сохраните правило отбора, источник и версию данных. Для модели укажите название, ревизию на Hugging Face и способ предобработки.

Посчитайте эмбеддинги и постройте индекс FAISS. Рядом с индексом сохраните таблицу, по которой можно открыть текст или изображение по ID. Укажите, как вы измеряете близость и почему выбрали эту меру. Например, для косинусной близости можно привести векторы каталога и запроса к единичной длине и сравнивать их по скалярному произведению. После сборки выведите число векторов, их размерность и число уникальных ID.

**При запуске Triton** одна модель на Python backend загружает индекс в память. Это единственная модель в каталоге Triton. Эмбеддинг вычисляет клиент: он берёт исходный объект, применяет ту же модель и предобработку, что и при сборке индекса, и отправляет серверу только вектор.

Для одиночного запроса подойдёт такой контракт: вход `EMBEDDING` типа `FP32[D]`, где `D` — размерность эмбеддинга; выход `NEIGHBOR_IDS` типа `INT64[5]`. Первым идёт ID ближайшего объекта. Отправьте также вектор неверной размерности: сервер должен вернуть ошибку, а затем успешно обработать следующий корректный запрос.

## Как проверить поиск

**1. Известный объект находит сам себя.** Выберите не менее десяти разных объектов из полного каталога. Для каждого Python-тест читает исходный текст или изображение, заново вычисляет эмбеддинг и отправляет его запущенному Triton. Проверьте, что все пять ID есть в каталоге, а первый — ID исходного объекта. Например, для фотографии № 417 первым должен вернуться 417. Тест должен пройти для каждого объекта.

Если у двух фотографий одинаковые эмбеддинги, обе окажутся на одном расстоянии от запроса. Для теста возьмите примеры с однозначным первым ответом и запишите, как обработали дубли.

**2. По новому запросу находится подходящий объект.** Подготовьте не менее десяти запросов, которых нет в индексе в таком виде. До запуска поиска запишите для каждого хотя бы один подходящий ID из каталога и объясните выбор. Посчитайте **Hit@5**: для какой доли запросов хотя бы один ожидаемый ID попал в первую пятёрку.

Разберите один ответ: покажите запрос и найденные тексты или снимки. Если все запросы оказались удачными, добавьте для разбора один трудный пример. Балл зависит от того, как вы проверили и объяснили результат; минимального значения Hit@5 нет.

## План работы

1. **Соберите прототип на 1 000 объектах.** Доведите один запрос до ответа Triton и откройте объект по первому ID. Измерьте время сборки и размер индекса, чтобы оценить затраты на полный каталог.
2. **Постройте полный индекс.** Обработайте 100 000 объектов партиями. Перезапустите сервер и убедитесь, что он читает готовый индекс без пересчёта эмбеддингов.
3. **Прогоните обе проверки на полном каталоге.** Если известный объект не находит себя, подайте один и тот же вектор в локальный FAISS и в Triton. Это поможет понять, на каком шаге расходятся ответы.
4. **Повторите запуск в чистом окружении.** Пройдите по командам своего README от получения индекса до запуска тестов. Исправьте шаги, где приходится вручную менять пути или догадываться, какую зависимость установить.

## Что сдавать

Пришлите **ссылку на репозиторий и хеш коммита**. В репозитории оставьте код подготовки данных и индекса, каталог модели Triton с конфигурацией, клиент и тесты. Большой индекс можно выложить отдельно: дайте ссылку и контрольную сумму. Скрипт сборки нужен и в этом случае.

В README укажите:

- Команды для подготовки данных, сборки или загрузки индекса, запуска сервера и тестов. Приведите версии зависимостей и образа Triton, расход оперативной памяти и места на диске при вашем запуске.
- Результаты обеих проверок на полном каталоге. Для одного вызова клиента покажите исходный объект, пять ID из ответа сервера и соответствующие им тексты или изображения.

## Как начисляются баллы

Каждое из двух условий в строке стоит 1 балл. Всего за проект можно получить 10 баллов, что даёт до 4 баллов в итоговой оценке курса. Например, 8 баллов за проект добавят 3,2 балла к итоговой оценке.

| Критерий | 1 балл | Ещё 1 балл |
|---|---|---|
| Данные и эмбеддинги | При повторном запуске скрипт отбирает те же объекты из указанной версии данных и присваивает им те же ID. | Предобученная модель с Hugging Face вычислила 100 000 эмбеддингов. Указаны ревизия модели, предобработка и размерность вектора. |
| Индекс FAISS | Сохранённый индекс загружается и находит соседей по выбранной мере близости. | В индексе 100 000 записей. По каждому возвращённому ID можно открыть соответствующий исходный объект. |
| Сервис Triton | В каталоге одна модель на Python backend. Она читает индекс при старте и использует его для следующих запросов. | Сетевой запрос возвращает пять ID нужного типа в порядке близости. Сервер отклоняет вектор неверной размерности и принимает следующий корректный запрос. |
| Проверки поиска | Python-тест заново кодирует не менее десяти исходных объектов. Для каждого сервис возвращает его ID первым. | Для новых запросов заранее указаны подходящие ID, посчитан Hit@5 и разобран один ответ. |
| Воспроизводимость и сдача | В чистом окружении по README можно получить индекс и запустить сервер с указанными версиями. | На сданном коммите проверяющий может повторить обе проверки. В README есть пример сетевого ответа с расшифровкой ID. |

Документация: [индексация и поиск в FAISS](https://github.com/facebookresearch/faiss/wiki/Getting-started) и [Python backend для Triton](https://github.com/triton-inference-server/python_backend).
