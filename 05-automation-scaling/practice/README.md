# Практика: Docker и Airflow

В прошлой практике мы запускали обучение из своего Python-окружения.
Теперь упакуем то же обучение Titanic в Docker-образ, сохраним результат вне контейнера
и поручим Airflow запускать шаги в нужном порядке.

К концу занятия вы сможете собрать образ из Dockerfile, передать контейнеру данные
и сохранить модель после удаления контейнера. Затем соберёте DAG из трёх задач
и по логу объясните причину неуспешного запуска.

## Шпаргалка по Docker

Команды ниже — справочник на время занятия. Их не нужно запускать подряд.
Вместо `CONTAINER` подставляйте имя или ID из `docker ps -a`.
Команды Compose выполняйте из папки с `compose.yaml`.

| Команда | Что делает |
| --- | --- |
| `docker pull python:3.13.12-slim` | Скачивает образ из registry. |
| `docker image ls` | Показывает локальные образы. |
| `docker build -t mlops-training:practice5 .` | Собирает образ из текущей папки и присваивает ему имя. |
| `docker run --rm mlops-training:practice5 --help` | Создаёт контейнер, запускает программу и удаляет контейнер после завершения. |
| `docker ps` / `docker ps -a` | Показывает работающие / все контейнеры, включая остановленные. |
| `docker logs -f CONTAINER` | Показывает stdout/stderr контейнера и новые строки по мере появления. |
| `docker exec -it CONTAINER sh` | Открывает оболочку внутри работающего контейнера. Выход — `exit`. |
| `docker stop CONTAINER` | Останавливает контейнер. |
| `docker rm CONTAINER` | Удаляет остановленный контейнер. |
| `docker volume ls` | Показывает тома Docker. |
| `docker compose build airflow` | Собирает образ сервиса Airflow по конфигурации Compose. |
| `docker compose up -d` | Создаёт и запускает сервисы в фоне. |
| `docker compose ps` | Показывает состояние сервисов текущего Compose-проекта. |
| `docker compose logs -f --tail 30 airflow` | Показывает последние 30 строк Airflow и продолжает вывод новых. |
| `docker compose exec airflow sh` | Открывает оболочку внутри работающего сервиса Airflow. |
| `docker compose down` | Останавливает и удаляет контейнеры и сеть проекта; named volumes сохраняются. |
| `docker compose down -v` | Дополнительно удаляет тома проекта вместе с их данными. |

Флаги для `docker run`: `--name NAME` задаёт имя контейнера, `-d` запускает его в фоне.
`-p 127.0.0.1:8080:8080` связывает локальный порт хоста с портом контейнера.
`-v путь_хоста:/data:ro` подключает каталог только для чтения; `-v имя_тома:/work` подключает volume.
Для контейнера с `--rm` после завершения уже не сработают `docker logs` и `docker exec`: контейнер удалён.

Справка: [Docker CLI](https://docs.docker.com/reference/cli/docker/).

Команды Compose: [Compose CLI](https://docs.docker.com/reference/cli/docker/compose/).

Прочитайте их входы и выходы: сейчас меняем способ запуска, ML-алгоритм уже написан.

Освежите в голове:

- Что фиксировал lock-файл в прошлых занятиях?
- Как проверить, что CSV не изменился?
- Что MLflow записывал о запуске, а что мы должны сохранить как файл модели?

Ответы для самопроверки:

**Lock-файл** фиксировал точные версии Python-пакетов, включая транзитивные зависимости — пакеты, которые нужны другим пакетам.
По нему менеджер зависимостей восстанавливает согласованное окружение.
Операционную систему и содержимое CSV lock-файл не фиксирует.

**Неизменность CSV** проверяем по SHA-256: вычисляем хеш файла и сравниваем с ранее сохранённым значением в `data/manifest.json`.
Если хеши совпали, содержимое файла совпадает с сохранённой версией.
В этой практике проверку выполняет `python3 check_env.py`.

**MLflow** записывал параметры обучения, validation ROC-AUC, размеры выборок и хеш данных для каждого запуска.
Обученную модель мы тоже сохраняли в MLflow как artifact — файл, связанный с запуском.
Параметры и метрика описывают результат обучения; файл `model.cbm` содержит саму обученную модель.
Он нужен, чтобы загрузить модель и получать предсказания без повторного обучения.
В текущей практике сохраняем этот файл в подключённый каталог или volume.

## 1. Собрать образ обучения

Образ содержит Python, зависимости и наш код. Контейнер — запущенный instance этого образа.
Dockerfile — текстовый файл с инструкциями сборки образа и настройками запуска контейнера.
Каждая инструкция начинается с имени, например `FROM` или `COPY`, после которого идут аргументы.
Порядок строк определяет последовательность сборки.

Основные инструкции нашей практики:

- `FROM python:3.13.12-slim` — выбирает базовый образ с Python и системными библиотеками.
- `WORKDIR /app` — задаёт рабочий каталог для последующих инструкций и программы; создаёт его, если каталога нет.
- `COPY requirements.txt .` — копирует файл из контекста сборки в рабочий каталог образа.
- `RUN pip install --no-cache-dir -r requirements.txt` — устанавливает зависимости при сборке образа.
- `ENV PYTHONUNBUFFERED=1` — задаёт переменную окружения; здесь Python выводит логи без задержки буферизации.
- `ENTRYPOINT ["python", "/app/pipeline.py"]` — задаёт программу, запускаемую при старте контейнера.

В других Dockerfile также встречаются `CMD`, `USER`, `ARG` и `EXPOSE`.
`USER airflow` выбирает пользователя для последующих `RUN` и запуска программы.
`ARG` задаёт параметр сборки, а `ENV` сохраняет переменную и для запуска контейнера.
`EXPOSE 8000` указывает предполагаемый порт приложения; доступ с хоста настраивают отдельно через `docker run -p`.

`CMD` задаёт команду по умолчанию, а при наличии `ENTRYPOINT` в JSON-форме — её аргументы.
Например, `CMD ["all"]` вместе с нашим `ENTRYPOINT` задаёт запуск `python /app/pipeline.py all`.
Аргумент `report` после имени образа в `docker run` заменит `all`, сохранив саму программу из `ENTRYPOINT`.
В этой практике аргументы передаём явно, поэтому добавлять `CMD` не требуется.

`RUN` выполняется во время `docker build`; `ENTRYPOINT` и `CMD` определяют запуск во время `docker run`.
Описание инструкций: [справочник Dockerfile](https://docs.docker.com/reference/dockerfile/).

Откройте `Dockerfile`: установка зависимостей уже написана.

В терминале компьютера создайте новый контейнер из того же образа:

Поэтому две оболочки в `training-shell` видели один файл `/app/note.txt`.

Файл был создан в доступном для записи слое контейнера `training-shell`; в образ его изменения не попали.
После выхода из первой оболочки контейнер завершился, а флаг `--rm` удалил его вместе с этим слоем.
Следующая команда `docker run` создала новый контейнер из исходного образа, в котором файла `note.txt` нет.

Он должен быть помечен `CACHED`: файл зависимостей не менялся, повторная установка пакетов не требуется.
Шаг `COPY pipeline.py .` выполнится заново, потому что содержимое Python-файла изменилось.
Сам комментарий не меняет поведение программы; здесь он нужен только для изменения содержимого файла.
По этой причине в Dockerfile сначала копируют requirements и устанавливают пакеты, а затем копируют код.

## 2. Передать данные и забрать модель

Bind mount подключает папку хоста к контейнеру через `-v путь_хоста:путь_контейнера`.
`$(pwd)` — абсолютный путь текущей папки.

Создайте папку для результатов:

```bash
mkdir -p out
```

В команде ниже `data` подключается к `/data` только для чтения (`:ro`),
а `out` — к `/work` для записи результатов. Файлы в `out` сохранятся после удаления контейнера.
Запустите все три шага обучения:

```bash
docker run --rm \
  -v "$(pwd)/data:/data:ro" \
  -v "$(pwd)/out:/work" \
  mlops-training:practice5 all
```

Ожидайте строки с `train_rows: 570`, `validation_rows: 143`, сохранением `model.cbm`
и результатом `passed: true`. Точное значение ROC-AUC программа запишет в отчёт.
Откройте `out/manual/metrics.json`: там метрика, параметры и хеши данных и модели.
В `out/manual/model.cbm` — сама модель.
Каталог `/work/manual` внутри контейнера соответствует `out/manual` на хосте.

Контейнер уже удалён. Запустите новый контейнер, который только читает результат:

```bash
docker run --rm \
  -v "$(pwd)/out:/work:ro" \
  mlops-training:practice5 report
```

Вы получите тот же `metrics.json` без повторного обучения.
Предскажите результат такой команды без `-v`, затем проверьте:

```bash

```

Ожидается `FileNotFoundError`: у нового контейнера своя файловая система.
Объясните, почему файл на хосте сохранился, но контейнер его не видит без монтирования.

## 3. Сохранить результат в volume

Volume — каталог хранения, которым управляет Docker. Мы обращаемся к нему по имени,
а физический путь на хосте выбирает Docker. Создайте отдельный том для этого опыта:

```bash
docker volume create mlops-practice5-models
```

Docker выведет имя тома. Запустите обучение, заменив только место записи результатов:

```bash
docker run --rm \
  -v "$(pwd)/data:/data:ro" \
  -v mlops-practice5-models:/work \
  mlops-training:practice5 all
```

Снова ожидайте `passed: true`. Теперь прочитайте результат новым контейнером:

```bash
docker run --rm \
  -v mlops-practice5-models:/work:ro \
  mlops-training:practice5 report
```

Отчёт сохранился после удаления контейнера. Папка `out` к этому запуску отношения не имеет.

**Bind mount** используют, когда контейнеру требуется доступ к конкретным файлам или каталогам хоста.
Типичные задачи — подключение исходного кода при разработке, конфигурационных файлов и локальных наборов данных.
Выбор этого механизма предполагает зависимость от путей и прав доступа на хосте.

**Volume** используют для постоянных данных приложения, расположением которых должен управлять Docker.\
Типичные задачи — хранение данных PostgreSQL, загруженных пользователями файлов и результатов обработки.\
Данные сохраняются после удаления контейнера; резервное копирование и перенос на другой хост организуют отдельно.

## 4. Передать порядок задач Airflow

**Apache Airflow** — система оркестрации: она организует выполнение задач по заданным зависимостям и расписанию.
Порядок работы описывают Python-кодом. Airflow запускает задачи, отслеживает их состояния и сохраняет историю запусков.
В веб-интерфейсе можно увидеть ход выполнения, прочитать логи и определить, на каком шаге возникла ошибка.

Для ML-пайплайна это полезно при регулярном обновлении модели: сначала нужно подготовить данные, затем обучить модель и проверить качество.
Обучение должно начинаться после успешной подготовки данных, а оценка — после успешного обучения.
Airflow управляет этими зависимостями; само обучение выполняет наш код CatBoost.
При временных сбоях для задач можно настроить повторные попытки.

Ранее команда `all` выполняла три функции последовательно в одном процессе.
Теперь каждый шаг станет отдельной задачей Airflow со своим статусом и логом.
На практике запустим пайплайн вручную; запуск по расписанию оставим дополнительным заданием.

**DAG** (Directed Acyclic Graph) — направленный граф без циклов, описывающий задачи и зависимости между ними.
Зависимость задаёт, какая задача должна завершиться раньше другой.
DAG run — один запуск всего графа; task instance — выполнение одной задачи в этом запуске.

Откройте `dags/titanic.py`. Декоратор `@dag` описывает граф, `@task` — его задачи.
Вызов функции с `@task` при построении DAG создаёт узел графа.
Тело функции выполнится позднее, когда Airflow запустит задачу.

Разобранный фрагмент `directory = prepare()` создаёт задачу и ссылку на её будущий результат.
Вызов `train(directory)` создаёт следующую задачу и зависимость от `prepare`.

В TODO 3 соберите цепочку из всех трёх задач. `prepare` возвращает путь к каталогу,
`train` принимает этот путь и возвращает его дальше, `evaluate` принимает один путь к каталогу, содержащему модель и validation.
Используйте результат одного вызова как аргумент следующего. Поддержите порядок:

```text
prepare -> train -> evaluate
```

Airflow передаёт между задачами короткую строку пути через XCom — механизм обмена результатами задач.
CSV и модель лежат в общем volume `/work`. Они не передаются через XCom.
Для каждого DAG run код создаёт отдельный каталог: повторный запуск не затрёт предыдущую модель.
Такой общий диск подходит для нашей локальной практики; для задач на разных серверах нужен общий доступ к хранилищу.

**Docker Compose** — инструмент для описания и совместного запуска контейнеров приложения: их образы, настройки, порты и тома задают в файле `compose.yaml`.
Его используют для локальной разработки, тестирования и развёртывания приложений на одном сервере, например сервиса вместе с базой данных.
В нашей практике Compose запускает один сервис Airflow и подключает к нему DAG, данные и постоянные тома.
Настройки сохраняются в файле, поэтому длинную команду `docker run` не нужно составлять при каждом запуске.

Флаг `-d` оставляет контейнер работать в фоне. Запустите Airflow:

```bash
docker compose up -d airflow
```

Ожидается контейнер в состоянии `Started` или `Running`. Посмотрите его вывод:

```bash
docker compose logs -f --tail 30 airflow
```

`-f` продолжает показывать новые строки, `--tail 30` сначала выводит последние 30 строк.
Первая инициализация может занять пару минут.

Остановите просмотр логов через Ctrl+C: контейнер продолжит работать.
Откройте [Airflow на своём ноутбуке](http://127.0.0.1:8080).\
В этой учебной конфигурации вход без пароля, порт доступен только через локальный адрес вашего компьютера.\
Режим `standalone` запускает компоненты Airflow вместе; это локальный стенд для обучения.

В списке DAG найдите `titanic_training`. Если его нет, откройте ошибки импорта в UI
или выполните `docker compose exec airflow airflow dags list-import-errors`.
Включите DAG переключателем и откройте граф. Вы должны видеть три узла и две связи.

Если виден один узел, вернитесь к TODO 3. Изменения DAG подхватываются без пересборки образа,
потому что папка `dags` подключена через bind mount.

На странице DAG `titanic_training` нажмите **«Запустить»** (в английском интерфейсе — **Trigger**).
Для первого запуска параметры вводить не нужно: `depth=4` и `min_auc=0.7` уже заданы в `params` внутри `dags/titanic.py`.
Подтвердите запуск.

Параметры задаются при создании нового запуска: вернитесь на страницу DAG `titanic_training` и нажмите **«Запустить»**.
В открывшемся окне «Запуск Dag-а» раскройте **«Расширенные параметры» → «Конфигурация JSON»**.
Конфигурация на странице уже созданного запуска доступна только для чтения; там изменить параметры нельзя.
Например, конфигурация первого запуска:

```json
{"depth": 4, "min_auc": 0.7}
```

Если интерфейс показывает отдельные поля `depth` и `min_auc`, значения можно изменить непосредственно в них.
Дождитесь статуса `success` у всех трёх задач.
Внутри запуска откройте задачу `evaluate`, затем её лог: найдите ROC-AUC и `passed: true`.

Путь `/work/<идентификатор>` виден в логе `prepare` и `train`.
Проверьте, что в UI подготовка завершается раньше обучения, а оценка начинается после обучения.

Скопируйте путь `/work/...` из лога `train` выбранного запуска: его `metrics.json` лежит в этом каталоге.

Чтобы увидеть сохранённые отчёты из терминала, выполните:

```bash
docker compose exec airflow python -c \
  'from pathlib import Path; [print(p, p.read_text()) for p in Path("/work").glob("*/metrics.json")]'
```

Появится минимум один отчёт с `passed: true`.
Compose описывает образ, команду, порт и монтирования в одном YAML-файле.
Откройте `compose.yaml`: найдите bind mount данных и два volume — для состояния Airflow и результатов.
Это другие тома, не `mlops-practice5-models` из прошлого опыта.

## 5. Найти причину падения

Запустите DAG ещё раз через кнопку **«Запустить»**. В окне запуска раскройте
**«Расширенные параметры» → «Конфигурация JSON»** и укажите:

```json
{"depth": 4, "min_auc": 1.0}
```

Подтвердите запуск.\
Первые две задачи должны завершиться успешно, `evaluate` — со статусом `failed`.\
Откройте лог именно упавшей задачи и найдите строку `ROC-AUC ... < threshold 1.0`.\
Отчёт сохраняется и при провале проверки, поэтому в новом `metrics.json` будет `passed: false`.

## Завершение

Остановите стенд:

```bash
docker compose down
```

Контейнер удалится, оба volume Compose сохранятся. После нового `docker compose up -d`\
история запусков и файлы моделей должны остаться на месте.\
Проверьте это до удаления результатов.\
Когда закончите, удалить именно тома этого стенда можно командой:

```bash
docker compose down -v
```

Команда удалит историю Airflow и модели этой практики. Для отдельного тома из шага 3:

```bash
docker volume rm mlops-practice5-models
```

Docker выведет имя удалённого тома. Папка `out` на хосте останется.
