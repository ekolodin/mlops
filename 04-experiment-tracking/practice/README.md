# Практика: трекинг экспериментов и мониторинг

Обучим три модели CatBoost на Titanic, сравним результаты в MLflow и загрузим
выбранную модель в HTTP-сервис. Затем измерим время ответа и найдём запрос,
завершившийся тайм-аутом, на графике и в логе.

MLflow хранит сведения о запусках обучения и файлы моделей. Prometheus собирает
метрики сервиса, Grafana показывает их на графиках.
TensorBoard показывает кривые обучения.

## Подготовка

Нужны Python 3.13, uv и терминал bash/zsh. Обучение работает на CPU.
uv устанавливает Python-зависимости и запускает команды в env проекта.
Для локального мониторинга установщик поддерживает macOS Intel/Apple Silicon
и Linux x86_64; на Windows можно использовать WSL.

Из корня своего клона репозитория `mlops` перейдите в папку практики:

```bash
cd 04-experiment-tracking/practice
uv sync --locked
uv run --locked python check_env.py
```

Проверка должна вывести версии библиотек и сообщение:

```text
Python 3.13; данные: 713 строк; SHA-256 совпадает
```

В `data/train.csv` — 713 пассажиров: 570 для обучения и 143 для валидации.
Отдельные 178 тестовых пассажиров не участвуют в выборе модели и сюда не включены.
`data/manifest.json` содержит описание подготовки и хеш CSV.

До занятия также скачайте Prometheus и Grafana:

```bash
bash monitoring.sh install
```

Бинарники сохраняются в `.tools/`; версии и SHA-256 заданы в `install_monitoring.py`.
Интернет нужен для установки зависимостей и скачивания бинарников. Дальше работаем локально.

Откройте четыре терминала в папке практики.


| Терминал | Что запускаем                                         |
| -------- | ----------------------------------------------------- |
| 1        | Обучение и выбор run, затем `service.py`              |
| 2        | Интерфейс MLflow                                      |
| 3        | TensorBoard, после его остановки — `load.py` и `curl` |
| 4        | Prometheus и Grafana через `monitoring.sh`            |




## 1. Записать эксперимент

Откройте `train.py`. Подготовка признаков и обучение уже написаны.
`Survived=1` — положительный класс: пассажир выжил.
Для ROC-AUC берём вероятность этого класса из `predict_proba(... )[:, 1]`.
Идентификатор пассажира и правильный ответ не входят в признаки.

В `tracking.py` заполните TODO 1 и 2. Run — один запуск обучения;
artifact — сохранённый файл, например модель. Run уже открыт в `train.py` через `mlflow.start_run()`.


| TODO                | Что записать                                                                   | Как проверить                                                    |
| ------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 1: `log_parameters` | Все `params`, размеры train/validation; тег `data_sha256`                      | `uv run --locked pytest -q tests/test_tracking.py -k parameters` |
| 2: `log_results`    | Метрику `validation_roc_auc`, CatBoost под именем `model`; вернуть `model_uri` | `uv run --locked pytest -q tests/test_tracking.py -k results`    |


Тег `data_sha256` хранит хеш CSV для сравнения данных между запусками.
Подсказки находятся рядом с TODO. Сигнатура модели — описание входа и выхода — уже подготовлена.

Выполните три запуска:

```bash
uv run --locked python train.py --depth 2 --name depth-2
uv run --locked python train.py --depth 4 --name depth-4
uv run --locked python train.py --depth 6 --name depth-6
```

Каждая команда выведет JSON с `run_id`, `validation_roc_auc` и `model_uri`.
У запусков разные ID, но одинаковые размеры выборок: 570 и 143.

Откройте второй терминал в той же папке и запустите интерфейс MLflow:

```bash
uv run --locked mlflow server --backend-store-uri sqlite:///state/mlflow.db \
  --host 127.0.0.1 --port 5001
```

Перейдите на [локальный MLflow](http://127.0.0.1:5001), откройте эксперимент
`titanic-tracking` и сравните три запуска. Посмотрите параметры, validation ROC-AUC
и сохранённую модель. Проверьте одинаковые `data_sha256` и `split_seed`.

## 2. Посмотреть обучение и восстановить модель

В третьем терминале, также из папки практики, запустите TensorBoard:

```bash
uv run --locked tensorboard --logdir state/tensorboard --host 127.0.0.1 --port 6006
```

На [странице TensorBoard](http://127.0.0.1:6006) откройте Scalars.
Имена кривых начинаются с `depth-2`, `depth-4`, `depth-6`, как имена запусков в MLflow.
При повторном запуске к имени папки добавляется номер: `depth-2-2`. Прошлые кривые сохраняются отдельно.

CatBoost записал кривые в `learn` и `test` каждого запуска.
Здесь `test` — название каталога CatBoost для переданного `eval_set`, то есть нашей validation-выборки.
Шаг графика — итерация бустинга. Сравните кривые обучения и валидации для одной метрики, например Logloss.

Заполните TODO 3 в `tracking.py`: загрузите модель по URI `runs:/<run_id>/model`.
URI указывает на модель конкретного запуска.

```bash
uv run --locked pytest -q tests/test_tracking.py
```

Ожидаем семь пройденных тестов. Они проверяют параметры, сохранение,
одинаковое разбиение и совпадение вероятностей до и после загрузки.

Скопируйте Run ID выбранного запуска из MLflow.
В первом терминале замените `RUN_ID` в команде на этот идентификатор:

```bash
course_run_id='RUN_ID'
uv run --locked python select_run.py "$course_run_id"
```

Команда проверит загрузку на трёх пассажирах и сохранит Run ID в `state/selected-run.json`. Сервис прочитает его при запуске.

## 3. Измерить запросы

Теперь измеряем работу сервиса. `status=ok` означает успешное выполнение запроса.

В `metrics.py` заполните TODO 4 и 5. Counter считает завершённые вызовы модели;
Histogram хранит распределение длительности, суммарное время и число вызовов. Метрики уже созданы.

В `count_request` выберите счётчик с метками `variant` и `status`, затем увеличьте его на один.
В `observe_duration` выберите гистограмму с меткой `variant` и запишите `seconds`.
`variant` принимает `normal/slow`, `status` — `ok/error`.
Не добавляйте `request_id` в метки: каждый новый ID создаст отдельный ряд.

Например, `prediction_requests_total{variant="normal",status="ok"} 12`
означает 12 успешных вызовов в нормальном режиме с момента запуска процесса.

```bash
uv run --locked pytest -q
```

Ожидаем 16 пройденных тестов. В приложении считаются вызовы `/predict`, прошедшие проверку входа.
Запросы `/health`, `/metrics/` и отклонённый вход с кодом 422 не входят в эти счётчики.
HTTP-маршруты и обработка ошибок написаны в `service.py`.

В первом терминале запустите приложение:

```bash
uv run --locked python service.py
```

Модель загружается один раз при запуске. В освобождённом третьем терминале выполните:

```bash
uv run --locked python load.py --seconds 10
curl -s http://127.0.0.1:8000/metrics/ | grep -E 'prediction_requests_total|prediction_duration_seconds_count'
```

Генератор выведет число успешных запросов и ошибок. В нормальном режиме ошибки
должны отсутствовать. В `/metrics/` найдите увеличение счётчика `normal/ok`;
число наблюдений гистограммы должно совпасть с числом завершённых вызовов.

`load.py` отправляет данные одного пассажира и ждёт ответ перед следующим запросом.
Поэтому при замедлении сервиса он отправляет меньше запросов в секунду.

## 4. Построить график

В четвёртом терминале из папки практики запустите мониторинг:

```bash
bash monitoring.sh
```

Скрипт держит два процесса запущенными; Ctrl+C остановит оба.
В [Prometheus](http://127.0.0.1:9090/targets) проверьте target `titanic` — адрес сервиса для сбора метрик.
Состояние должно стать **UP**.
Prometheus раз в две секунды читает `/metrics/` приложения и сохраняет историю значений.

Откройте [Grafana](http://127.0.0.1:3000), войдите как `admin` с паролем `seminar`.
В Dashboards → MLOps найдите «Titanic: запросы модели».
Источник данных и две панели уже настроены.

Панель «Запросы в секунду» использует `rate`: средний прирост счётчика в секунду
за последнюю минуту. Доля технических ошибок делит частоту ошибок на частоту всех вызовов.
Без запросов доля ошибок не определена, поэтому график может быть пустым.

На третьей панели откройте меню → Edit. В Queries выберите Code и вставьте:

```promql
sum by (variant) (rate(prediction_duration_seconds_sum{job="titanic"}[1m]))
/
sum by (variant) (rate(prediction_duration_seconds_count{job="titanic"}[1m]))
```

Числитель — прирост суммарного времени обработки; знаменатель — прирост числа вызовов.
Отношение даёт среднюю длительность в секундах. Время включает ожидание до тайм-аута,
но не сетевую задержку между клиентом и приложением.

Назовите панель «Средняя длительность, с». Примените изменения панели и сохраните дашборд.
Запустите нагрузку:

```bash
uv run --locked python load.py --seconds 30
```

Графики появятся, когда Prometheus соберёт несколько измерений во время нагрузки.

## 5. Найти тайм-аут

Остановите только приложение в первом терминале через Ctrl+C.
MLflow и мониторинг оставьте работающими. Запустите тот же выбранный run с учебным замедлением:

```bash
uv run --locked python service.py --slow-every 5
```

Каждый пятый вызов искусственно ждёт 1.2 секунды перед вычислением.
Приложение ограничивает ожидание одной секундой и возвращает HTTP 504.
Модель та же; задержка добавлена в коде сервиса для воспроизведения тайм-аута.

В третьем терминале:

```bash
uv run --locked python load.py --seconds 60
```

Посмотрите графики для `slow`: должны появиться ошибки и увеличиться средняя длительность.
Счётчики сбросились при перезапуске процесса; `rate` учитывает такие сбросы.
Для сравнения видны отдельные ряды `normal` и `slow`.

Найдите `request_id` одного ответа 504 в выводе генератора, затем ту же строку в логе приложения.
В логе должны быть `TimeoutError`, `model_inference` и `timeout=1.0s`.

Остановите приложение и верните нормальный режим:

```bash
uv run --locked python service.py
```

Повторите нагрузку. Новые запросы должны проходить без тайм-аутов;
график реагирует с задержкой, потому что использует последнее минутное окно.

## Проверка результата

- В MLflow сохранены три запуска с параметрами, метрикой и моделями.
- Выбранная модель загружается; после загрузки её предсказания совпадают с исходными.
- Grafana показывает частоту запросов, долю ошибок и среднюю длительность.
- `request_id` связывает ответ 504 с записью о тайм-ауте в логе.
