# ДЗ-2. Одна модель, два интерфейса: Docker и gRPC

Вам необходимо реализовать сервис, который принимает фотографию и возвращает её описание на английском языке. Модель SmolVLM-256M-Instruct и клиент проверки уже готовы. Ваша задача — запустить HTTP и gRPC из одного Docker-образа и убедиться, что на одну фотографию с одинаковыми параметрами оба сервиса возвращают одинаковую подпись.

**Оценка — сдал / не сдал.**

## Зачем мы это делаем

Пока модель вызывают из Python, клиенту нужны её веса и зависимости. Если модель работает в отдельном сервисе, клиенту достаточно отправить фотографию. В этой работе вы проверите, что при переходе от прямого вызова к сетевому запросу модель получает те же байты и выдаёт ту же подпись.

## Введение: как фотография попадает в модель

В HTTP-запросе фотография приходит как строка base64 внутри JSON. В gRPC клиент вызывает метод `Predict` и передаёт байты файла в сообщении Protobuf. Файл `.proto` описывает поля этого сообщения. По нему генерируются классы Python, которыми пользуются клиент и сервер.

Например, для `cats.jpg` HTTP-обработчику сначала нужно раскодировать строку. После этого оба обработчика передают одни и те же байты в `CaptionInput` и вызывают модель. Поэтому эталон для сравнения — прямой вызов модели из Python.

### Рабочий пример: проверка модели без сервиса

Скопируйте папку ДЗ целиком и перейдите в `starter/`; рядом с ним должен лежать каталог `assets/`. Все команды ниже выполняйте из `starter/`.

- Скачайте веса (около 518 МБ) и запустите тесты готовой части. Скрипт `run_tools.sh` запускает команды в Docker:

  ```bash
  bash run_tools.sh python download_model.py
  bash run_tools.sh pytest -q tests/test_given.py
  ```

  Должны пройти все 9 тестов из `test_given.py`. Остальные тесты запускайте после реализации контракта и обработчиков.

## Контракт сервиса

| Свойство | Требование |
|---|---|
| Изображение | JPEG или PNG; максимум 1 048 576 байт и 1 048 576 пикселей |
| Лимит `max_new_tokens` | От 1 до 48 включительно; при пропуске поля модель использует 24 |
| Ответ | `caption` — подпись, `model_version` — версия модели, `image_sha256` — хеш исходных байтов, `request_id` — уникальный ID вызова |
| Неверный вход | HTTP возвращает 422, gRPC — `INVALID_ARGUMENT` |

Для gRPC зафиксированы имена, номера и типы полей:

| Сообщение | Поля: номер, тип и имя |
|---|---|
| `CaptionRequest` | 1: `optional bytes image`; 2: `optional int32 max_new_tokens` |
| `PredictionResponse` | 1: `string caption`; 2: `string model_version`; 3: `string request_id`; 4: `string image_sha256` |

## Этапы выполнения

### 1. HTTP и gRPC

Модель уже загружается один раз при запуске каждого сервиса. HTTP-обработчикам она доступна как `app.state.runner`, классу `Predictor` — как `self.runner`.

**HTTP**

- В `GET /health` верните JSON с `ready: true` и версией загруженной модели в поле `model_version`.
- В `POST /predict` декодируйте `image_base64` с проверкой base64. Передайте байты и лимит токенов в `CaptionInput` и верните результат `runner.predict(value, protocol="http")`. При неверной кодировке или недопустимом изображении верните HTTP 422.

**gRPC**

- В [predict.proto](starter/proto/predict.proto) опишите сообщения метода `Predict` по таблице в разделе «Контракт сервиса».
- В `Predict` передайте байты изображения напрямую. Используйте `HasField`, чтобы отличить пропущенный лимит от нуля. Если поле пропущено, передайте в модель `None`; явный ноль отклоните.
- При отсутствии изображения или ошибке валидации верните `INVALID_ARGUMENT`. Для корректного запроса вызовите `runner.predict(value, protocol="grpc")` и верните все четыре поля результата.
- В `build_grpc_server(runner)` создайте сервер с пулом потоков, зарегистрируйте в нём `Predictor` и верните сервер. Выбор порта и запуск уже написаны.

**Тесты**

- Добавьте в `tests/` два теста: один на допустимую границу, другой на неверный вход. Можно проверить `CaptionInput` напрямую или вызвать обработчик. Выберите случаи, которых нет в выданных тестах и `check.py`; смена протокола для того же входа не считается новым случаем.
- Сгенерируйте классы из контракта и запустите все тесты:

  ```bash
  bash run_tools.sh python -m grpc_tools.protoc -Iproto \
    --python_out=. --grpc_python_out=. proto/predict.proto
  bash run_tools.sh pytest -q
  ```

### 2. Запустите оба сервиса

- В [Dockerfile](starter/Dockerfile) используйте базовый образ `python:3.13.12-slim`. Установите зависимости из `requirements.txt` с `--extra-index-url https://download.pytorch.org/whl/cpu`.
- Скопируйте `model.py`, `service.py` и `proto/` в образ. Сгенерируйте классы Protobuf при сборке. Веса и журнал оставьте вне образа.
- Задайте `MODEL_DIR=/models`, `LOG_PATH=/logs/requests.jsonl`, `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`. Настройте точку входа `python service.py`, которая принимает аргумент `http` или `grpc`.
- Соберите образ и создайте общий том для журнала:

  ```bash
  docker build -t hw2:model .
  docker volume create hw2-logs
  ```

- Запустите из этого образа два контейнера в сети `hw2-network` (её уже создал `run_tools.sh`). В каждом подключите `../assets` только для чтения, а том `hw2-logs` — для записи:

  ```bash
  docker run -d --name hw2-http --network hw2-network -p 127.0.0.1:8000:8000 \
    --mount type=bind,source="$PWD/../assets",target=/models,readonly \
    --mount type=volume,source=hw2-logs,target=/logs \
    hw2:model http
  docker run -d --name hw2-grpc --network hw2-network -p 127.0.0.1:50051:50051 \
    --mount type=bind,source="$PWD/../assets",target=/models,readonly \
    --mount type=volume,source=hw2-logs,target=/logs \
    hw2:model grpc
  ```

- Проверьте готовность HTTP командой `curl http://127.0.0.1:8000/health`: ожидайте `ready: true` и версию модели. Для gRPC проверьте вывод `docker logs hw2-grpc`: в нём должна появиться строка `gRPC ready`.

### 3. Проверьте результат

- **Ответы модели.** Запустите клиент. Он проверит четыре запроса: для каждого подпись, версия модели и хеш изображения должны совпасть в Python, HTTP и gRPC. У каждого сетевого запроса должен быть свой ID.

  ```bash
  bash run_tools.sh python check.py \
    --http http://hw2-http:8000 --grpc hw2-grpc:50051 --report state/responses.json
  ```

  Ожидаемая последняя строка: `OK: 4 captions × Python/HTTP/gRPC; 6 shared invalid inputs + invalid HTTP base64`.

- **Права на модель.** Попробуйте записать файл в каталог модели. Ожидаемая ошибка — `Read-only file system`:

  ```bash
  docker exec hw2-http python -c \
    'from pathlib import Path; Path("/models/write-probe").write_text("x")'
  ```

- **Общий журнал.** В `state/responses.json` выберите ответ с `"protocol": "grpc"`. Его `request_id` должен быть виден из HTTP-контейнера: проверьте вывод `docker exec hw2-http cat /logs/requests.jsonl`.
- **Сохранность журнала.** Удалите оба контейнера (`docker rm -f hw2-http hw2-grpc`). Повторите команду запуска HTTP из шага 2 с тем же томом и найдите в журнале тот же `request_id`. Затем удалите контейнер командой `docker rm -f hw2-http`, чтобы освободить имя. Том сохранится.
- **Запуск без весов.** Подключите пустой каталог вместо модели. Сервис должен завершиться с ошибкой `Model files missing`:

  ```bash
  empty_dir=$(mktemp -d)
  docker run --rm --mount type=bind,source="$empty_dir",target=/models,readonly hw2:model http
  ```
